## Волна 1 — Фундамент

### 1.1 Function Calling

**Что сейчас:** Ничего. Агент умеет только отвечать текстом. В схеме есть `MessageType.TOOL`, но инфраструктуры вызова функций нет.

**Что нужно сделать:**
- Создать модель `AgentFunction` (название, тип, параметры подключения, JSON-схема)
- UI раздел "Функции" в карточке агента (включить/выключить, ввести токен/URL)
- Передача определений функций в LLM как `tools` (формат OpenAI function calling)
- Исполнитель функций на стороне gateway/orchestrator (ai-master)
- Универсальные типы: webhook, HTTP-запрос, CRM-действие, Google Sheets

**Сложность:** Высокая — архитектурная задача, затрагивает gateway + orchestrator + UI + DB
**Риск:** Средний — ошибки в исполнении функций могут повлиять на внешние системы клиентов

**Подводные камни:**
- Безопасность: агент вызывает внешние API с данными клиента — нужна валидация и санитизация
- Retry-логика: что делать если webhook не отвечает?
- Биллинг: каждый вызов функции = доп. расход PU?
- Таймауты: LLM ждёт ответ от внешнего API — нужен async-паттерн

### 1.2 Inbox / Диалоги

**Что сейчас:** UI готов на моках (`components/inbox/`). Есть `InboxLayout`, `ChatThreadView`, кнопка "Взять диалог", фильтры по каналам, sentiment-индикаторы. Нет реального бэкенда — все данные из `mocks/inbox.ts`.

**Что нужно сделать:**
- Модели в Prisma: `Conversation`, `ConversationMessage`, `ConversationParticipant`
- Реал-тайм обновления (WebSocket или SSE)
- API для списка диалогов, фильтрации, поиска
- Механизм "перехвата" диалога оператором (пауза AI, ручной ответ)
- Режимы работы: автопилот / подсказка / ручной / мониторинг
- Уведомления: эскалация, таймаут без ответа, ключевые слова

**Сложность:** Высокая — самая объёмная задача, много UI + реал-тайм + бизнес-логика
**Риск:** Высокий — это ядро платформы, ошибки = потерянные сообщения клиентов

**Подводные камни:**
- WebSocket: нужен отдельный WS-сервер или интеграция с Next.js (не нативно поддерживается в App Router)
- Конкурентность: два оператора могут одновременно взять один диалог
- Масштаб: при 100+ операторах онлайн нагрузка на WS резко растёт
- Состояние: переключение AI↔оператор должно быть атомарным и без потери сообщений

### 1.3 Память агента

**Что сейчас:** `AgentMessage` хранит историю чата, `AgentSummary` — саммари по `telegramUserId`. Нет профиля клиента, нет долгосрочной памяти между сессиями.

**Что нужно сделать:**
- Модель `CustomerProfile` (имя, контакты, история, заметки, предпочтения)
- Связка: telegramUserId / whatsappId / email → единый профиль
- Автоматическое извлечение фактов из диалогов (LLM-based)
- Векторное хранение фактов (ChromaDB уже используется)
- UI для оператора: просмотр и редактирование профиля

**Сложность:** Средняя
**Риск:** Низкий — можно внедрять постепенно

**Подводные камни:**
- Дедупликация: один клиент может писать из Telegram и Email — нужен merge профилей
- GDPR/ПДн: хранение персональных данных клиентов требует согласия
- Качество автоизвлечения: LLM может неправильно "запомнить" факт

### 1.5 Битрикс24

**Что сейчас:** Ничего. Нет кода интеграции.

**Готовое решение:** REST API Битрикс24 — полноценный, хорошо документированный.

| Подход | Что можно | Сложность подключения |
|--------|-----------|----------------------|
| **Входящий webhook** | Создавать лиды, сделки, контакты | 1 клик — пользователь создаёт webhook в Б24 |
| **Исходящий webhook** | Получать события (новый лид и т.д.) | Просто — настройка в UI Б24 |
| **Локальное приложение** | Боты, Open Channels, события | Средне — пользователь регистрирует приложение |
| **Маркетплейс** | Одна кнопка "Установить" | Сложно — ревью Битрикс24 |

**Рекомендация:** Начать с **входящего webhook** (пользователь вставляет URL). Позже — OAuth через локальное приложение для Open Channels.

**Стоимость:** API бесплатно на всех тарифах. Open Channels — от тарифа "Стандартный".

**Rate limit:** 2 req/s на webhook, есть batch до 50 команд за запрос.

**Нужно ли своё приложение в Битрикс24?**
- Для CRM (лиды/сделки) — **НЕТ**, хватит webhook
- Для Open Channels (бот в чате) — **ДА**, нужно локальное приложение
- Маркетплейс — пока не нужен, слишком рано

**npm:** `@2bad/bitrix` или простой `fetch` wrapper

**Подводные камни:**
- Rate limit 2 req/s очень низкий — обязательно использовать batch
- Webhook URL содержит токен — если утечёт, доступ ко всему CRM
- У клиентов разные версии Б24 (облако vs коробка) — разные URL и возможности
- Open Channels требуют регистрации бота через API `imbot.register` — сложнее чем webhook

## Волна 2 — Каналы и масштаб

### 2.1 WhatsApp

**Что сейчас:** Иконка есть, бэкенда нет.

**Варианты подключения:**

| Сервис | Цена | API | Подключение | Риск бана |
|--------|------|-----|-------------|-----------|
| **GreenAPI** | от 990 ₽/мес | REST, SDK для Node.js | 1 клик (API-ключ + webhook) | Средний |
| **Wazzup** | от 1500 ₽/мес | REST, CRM-ориентированный | Просто (API-ключ + webhook) | Средний |
| **Chat2Desk** | от 3000 ₽/мес | REST | Средне (тяжёлая платформа) | Низкий |
| **Edna** | от 15000 ₽/мес | REST, enterprise | Сложно (sales-процесс + верификация Meta) | Нет |
| **Baileys** (open-source) | Бесплатно | Своя обёртка | Сложно (self-hosted) | Высокий |

**Рекомендация для MVP:** **GreenAPI** — самый простой API, есть free tier для разработки, webhook из коробки.

**Рекомендация для прода:** **Edna** или **Chat2Desk с WABA** — официальный WhatsApp Business API, нет риска бана.

**Архитектура:** Аналог Telegram-интеграции: GreenAPI webhook → `/api/gateway/whatsapp` → orchestrator → ответ через GreenAPI send API.

**Подводные камни:**
- Неофициальные шлюзы (GreenAPI, Wazzup) — номер может быть заблокирован Meta
- Официальный WABA (Edna) — нужна верификация Meta Business (2-4 недели)
- У GreenAPI/Wazzup телефон должен быть онлайн (multi-device решает, но бывают сбои)
- WhatsApp запрещает mass-рассылки через неофициальные каналы

### 2.2 Email (Gmail, Yandex, Mail.ru)

**Что сейчас:** Нет email-канала. Resend используется для отправки системных писем (верификация).

| Провайдер | Чтение | Отправка | OAuth | Стоимость |
|-----------|--------|----------|-------|-----------|
| **Gmail** | Gmail API + Pub/Sub push | Gmail API / SMTP | OAuth 2.0 (верификация Google 2-6 нед.) | Бесплатно |
| **Yandex** | Только IMAP | SMTP | OAuth через Yandex ID | Бесплатно |
| **Mail.ru** | Только IMAP | SMTP | OAuth через VK ID | Бесплатно |
| **Любой** | IMAP (imapflow) | SMTP (nodemailer) | App-пароль | Бесплатно |

**Рекомендация:** Универсальный IMAP/SMTP через `imapflow` + `nodemailer`. Gmail API + Pub/Sub как premium-вариант для push-уведомлений.

**npm:** `imapflow` (от автора nodemailer, активно поддерживается), `nodemailer`

**Подводные камни:**
- **Gmail OAuth верификация** — Google требует privacy policy, homepage, скринкаст. Процесс 2-6 недель
- **IMAP polling** — не реал-тайм (задержка 1-5 мин), каждое подключение = сокет, при 1000+ ящиков — нужен worker-пул
- **IMAP IDLE** — push-нотификации, но соединение нужно пересоздавать каждые 29 мин
- **Yandex/Mail.ru** — нет API для почты, только IMAP. Пользователь должен включить IMAP вручную
- **Тредирование** — определить, это новое письмо или ответ в треде (In-Reply-To / References заголовки)
- **HTML-парсинг** — письма приходят в HTML, нужна конвертация в текст для агента
- **Вложения** — могут быть большие файлы, нужны лимиты
- **Спам** — исходящие ответы агента могут попадать в спам

### 2.3 Jivo Chat

**Что сейчас:** Ничего.

**Готовое решение:** Jivo Webhook Bot API — бот получает все входящие сообщения через webhook, отвечает JSON.

**Подключение:** Средне — пользователь должен быть на тарифе Professional ($38/оператор/мес). Настройка webhook URL в developer-кабинете Jivo.

**Стоимость для клиента:** Входит в их тариф Professional.

**Разработка на нашей стороне:** Низкая сложность — обработка POST-запросов + ответ JSON.

**npm:** Нет SDK, простой HTTP.

**Подводные камни:**
- Ответ бота должен вернуться за **5 секунд** (таймаут Jivo) — если LLM думает дольше, нужен async-ответ
- Когда чат передан оператору, бот перестаёт получать сообщения
- Нет возможности получить историю чатов через API — только реал-тайм
- Документация на русском полнее, чем на английском, но всё равно скудная
- Бесплатный тариф Jivo **не поддерживает** API — клиент должен быть на платном тарифе

### 2.4 ВКонтакте

**Что сейчас:** Ничего.

**Готовое решение:** VK Bots API — полностью бесплатный, хорошо документированный.

**Подключение:** Просто — токен сообщества + Callback API (webhook). Пользователь создаёт сообщество VK, генерирует токен, вводит в настройках агента.

**Стоимость:** Бесплатно.

**npm:** `vk-io` — рекомендуется, TypeScript, хорошо поддерживается, ~8K downloads/week.

**Подводные камни:**
- Rate limit: 20 req/s — достаточно для большинства сценариев
- Бот не может писать первым — только отвечать пользователям, которые сами написали в сообщество
- `random_id` обязателен при отправке (защита от дублей) — не забыть генерировать
- Пользователь должен включить "Сообщения сообщества" в настройках группы VK
- Подтверждение сервера: VK отправляет confirmation-строку, нужно вернуть её из endpoint

### 2.5 amoCRM

**Что сейчас:** Ничего.

**Готовое решение:** REST API v4 — хорошо документированный, OAuth 2.0.

**Подключение:**
- Вариант A: Пользователь создаёт интеграцию в amoCRM, генерирует long-lived ключ → вставляет в LEO (почти 1 клик)
- Вариант B: OAuth 2.0 flow через нашу интеграцию (сложнее, но удобнее для клиента)

**Стоимость:** API входит во все платные тарифы amoCRM (от 499 ₽/пользователь/мес). Бесплатного тарифа нет.

**Возможности:** Создание лидов, контактов, сделок. Вебхуки на события. Salesbot-шаг через webhook.

**npm:** `amocrm-js` или свой fetch-wrapper.

**Подводные камни:**
- **Refresh token одноразовый!** Потеря нового refresh-токена = потеря доступа навсегда. Нужна надёжная персистенция токенов
- Rate limit: 7 req/s — низкий, но batch до 250 сущностей за запрос
- Webhook payload в формате `application/x-www-form-urlencoded` (НЕ JSON) — неожиданно
- Кастомные поля: у каждого клиента свои, нужен маппинг полей в UI

### 2.6 Авито

**Что сейчас:** Ничего.

**Готовое решение:** Avito Messenger API — официальный.

**Подключение:** OAuth 2.0. Нужна регистрация на developers.avito.ru + одобрение заявки.

**Стоимость:** Бесплатно.

**Подводные камни:**
- **Одобрение заявки** может занять время — Авито ревьюит use-case
- Нельзя писать первым — только отвечать в существующих чатах
- Нет форматирования — только текст и изображения
- Webhook может задерживаться — нужен polling как fallback
- Каждый вызов привязан к конкретному продавцу (OAuth-токен per user)

### 2.7 1С

**Что сейчас:** Ничего.

**Есть ли готовое API?** Нет универсального.

| Подход | Сложность | Нужна работа на стороне клиента? |
|--------|-----------|----------------------------------|
| OData (авто-REST) | Средняя | Минимальная (включить в настройках 1С) |
| HTTP-сервисы 1С | Высокая | Да, нужен 1С-разработчик |
| Файловый обмен (CommerceML) | Средняя | Настройка выгрузки |
| Middleware-агент | Очень высокая | Установка агента в сети клиента |

**Рекомендация:** Не делать в ближайших волнах. Предложить клиентам:
- Интеграцию через **универсальный webhook** (Function Calling из п.1.1)
- Или через **МойСклад** как прокси (у МойСклад есть REST API + синхронизация с 1С)

**Подводные камни:**
- У каждого клиента уникальная конфигурация 1С — нет "одного API"
- 1С обычно за файрволом — нужен VPN или reverse-proxy
- OData экспонирует данные с русскими именами полей (`Справочник_Номенклатура`)
- Производительность OData на больших данных — плохая
- **Безопасность:** публикация 1С в интернет — кошмар для безопасников клиента
- Стоимость 1С-разработчика на стороне клиента — отдельная статья расходов

### 2.8 Транскрибатор

**Что сейчас:** Ничего. Голосовые сообщения не обрабатываются.

| Сервис | Цена | Русский язык | Подключение |
|--------|------|-------------|-------------|
| **OpenAI Whisper API** | $0.006/мин ($0.36/час) | Отлично | 1 вызов API, просто |
| **Deepgram** | $0.0043/мин (Nova-2) | Хорошо | REST API, есть $200 free credit |
| **Yandex SpeechKit** | ~₽1.2/15 сек (~$0.20/час) | Лучше всех для RU | REST API, нужен Yandex Cloud |
| **Self-hosted Whisper** | Бесплатно (GPU ~$0.75/час) | Отлично | Сложно, нужен GPU-сервер |

**Рекомендация:** **OpenAI Whisper API** для MVP (дёшево, просто, отличный русский). **Yandex SpeechKit** как альтернатива для RU-рынка.

**Реализация:**
- Получаем голосовое из Telegram/WhatsApp → скачиваем файл → отправляем в Whisper → текст → агенту
- Один API-вызов, ~10-30 сек задержка на 5 мин аудио

**Подводные камни:**
- Telegram отдаёт голосовые в формате .ogg (Opus) — Whisper принимает, но нужно проверить
- WhatsApp через GreenAPI — формат может отличаться, возможна конвертация через ffmpeg
- Лимит Whisper: 25 MB на файл — длинные голосовые нужно разбивать
- Биллинг: каждая минута транскрипции = доп. расход PU клиента
- Ошибки распознавания: агент может получить неверный текст, особенно с именами/адресами

### 2.9 Расширенный биллинг

**Что сейчас:** PU-система работает. Трекается: LLM-токены по типам, стоимость в USD, PU списание. Есть уведомления при 80% и 100% использования.

**Что нужно добавить:**
- Новые типы операций в PU: транскрипция, браузерная сессия, embeddings
- Детальная разбивка в ЛК клиента (сколько на LLM, сколько на транскрипцию и т.д.)
- Настраиваемые лимиты по типам операций в тарифных планах
- Автоостановка агентов при нулевом балансе (настраиваемая)

**Сложность:** Средняя — расширение существующей системы
**Риск:** Средний — ошибки в биллинге = потеря денег или доверия

**Подводные камни:**
- Гонка условий: параллельные списания могут привести к отрицательному балансу
- Ретроактивные корректировки: что если транскрипция прошла, но потом ошибка?
- Курс PU→₽ для разных операций — нужен конфигурируемый прайс-лист
- Отчётность: клиенты захотят выгрузку для бухгалтерии

### 2.10 Автообучение по сайту

**Что сейчас:** Apify интегрирован (`lib/apify.ts`), парсинг сайта работает (`/api/ai/parse-website`). Нет автоматического пересканирования.

**Что нужно добавить:**
- Cron-задача: пересканирование сайта клиента каждые N дней
- Diff-обнаружение: обновлять только изменившиеся страницы
- Настройка в карточке агента: URL, глубина, исключения, частота
- Автоматическое обновление базы знаний (удаление устаревших chunks, добавление новых)

**Варианты реализации:**

| Вариант | Стоимость | Плюсы | Минусы |
|---------|-----------|-------|--------|
| **Apify** (текущий) | $0.50-2/1000 стр | Уже интегрирован | Платный, зависимость |
| **Crawlee** (self-hosted) | Бесплатно | Open-source, от авторов Apify | Нужен свой сервер |
| **Firecrawl** | от $16/мес | Markdown-ready вывод | Ещё одна зависимость |

**Рекомендация:** Оставить Apify для сложных JS-сайтов, добавить Crawlee для простых/плановых краулов.

**Подводные камни:**
- Apify free tier ($5/мес) — хватит на ~200-500 страниц, для прода мало
- robots.txt: нужно уважать, иначе юридические проблемы
- Динамические SPA-сайты — нужен Playwright-рендеринг (дороже)
- Удаление устаревшего контента из ChromaDB — нужна логика diff + cleanup
- При большом количестве клиентов плановый краулинг может стать дорогим

## Общие подводные камни

### Архитектурные

1. **WebSocket в Next.js App Router** — не поддерживается нативно. Варианты:
   - Отдельный WS-сервер (Socket.io / ws) рядом с Next.js
   - Pusher / Ably как managed-сервис ($25-49/мес)
   - Server-Sent Events (SSE) — проще, но только server→client

2. **Единая модель диалога** — сейчас `AgentMessage` привязан к `telegramUserId`. При добавлении WhatsApp, Email, VK, виджет — нужна абстракция `Conversation` с привязкой к каналу и единому `CustomerProfile`.

3. **Gateway (ai-master)** — большинство интеграций каналов затрагивают gateway. Нужно убедиться что архитектура gateway готова к multi-channel.

### Юридические

4. **ПДн (152-ФЗ)** — хранение имён, телефонов, email клиентов пользователей. Нужна политика обработки ПДн, согласия, DPA с клиентами.

5. **Рассылки** — любая автоматическая отправка сообщений клиентам (через бота, email, WhatsApp) — это рассылка по 152-ФЗ и закону о рекламе. Нужно согласие получателя.

### Операционные

6. **Зоопарк токенов** — каждая интеграция = свой OAuth/API-ключ на клиента. Нужно безопасное хранение (шифрование в БД), ротация, обработка отзыва.

7. **Мониторинг каналов** — каждый канал может "упасть" (токен протух, webhook не отвечает). Нужен health-check и алертинг.

8. **Порядок внедрения** — зависимости между фичами:
   - Function Calling → Битрикс24/amoCRM/1С (без FC нет CRM-действий)
   - Inbox → все каналы (без Inbox нет supervision)
   - Память → Шаблоны с переменными (без памяти неоткуда брать `{{имя}}`)
   - Виджет → Форма лидов → CRM (цепочка зависимостей)
